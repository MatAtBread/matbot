`plugin remove` takes back what `plugin add` created, and only that (issue #98). A github/http plugin's cache — its source, the dependencies installed into it, its set-aside copy and its name link — is matbot's own and derivable from the config entry, so `remove` deletes it unless another configured plugin's files share the directory; a removed plugin is no longer importable by name, nor listed by `discover_local`. What an install changes in the project — an npm package, or the `node_modules` and lockfile a local plugin's dependency install creates — is recorded under `.plugins/.installs/` as it is created (by `plugin add` and `matbot install`), and `remove` offers back exactly that (`npm-uninstall`, and a new `remove-provisioned` gate), never a package the project declared itself. What `add` cannot carry through or take back exactly it refuses before anything is asked or written, saying what to do instead: an npm plugin is installed by its package name only (no version, tarball or git URL), is checked for `matbotRuntime` before it is installed (`npm view`), is configured as it is when the project already has it installed, and needs a project `package.json`; a duplicate name is refused before installing; a local plugin's dependencies are installed only into a directory with no `node_modules` and no lockfile, and a failed install removes what it wrote. An `add` that disowns the plugin after installing it takes back exactly what it created, unasked; a provider's `module:` keeps a shared cache on `remove`; the name link follows the copy materialised last instead of the first; and `plugin add npm:<name>` no longer hands the package manager an `npm:` it reads as an alias, and is refused when something local also answers to the name, which the recorded entry would load instead.
