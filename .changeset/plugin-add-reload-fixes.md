`plugin add` and `plugin reload` fixed from a live install (issue #90). **A refresh no longer evicts what `add` installed**: a fetched plugin's dependencies live in its own `.plugins/` cache directory, which is the subtree a refresh dropped whole — so `reload` was structurally impossible for every http plugin with a dependency. Only the fetched half is dropped now. **A fetched plugin's dependencies are planned before it is loaded**: `add` lists them in the approval for the plugin itself and loads it once they are installed, and a `reload` whose refreshed manifest declares a new one offers it (`provision-deps`) before loading that copy — declined, the working copy is restored. Both used to load first, fail on the first missing import with an error and a stack in the log, then ask and retry; and the log note and resolve error that said this route "installs no dependencies" now say how it gets them. **A failed reload is a no-op, not an outage**: the evicted source is set aside rather than deleted, so a reload whose load fails restores the copy that was working and loads that, reporting which happened. And an install that fails on a workspace-provided peer is explained rather than mis-advised — `describeInstallFailure` recognises an unresolvable *dependency* of the package asked for in a pnpm workspace and names the setting (pnpm >= 10 reads `linkWorkspacePackages` from `pnpm-workspace.yaml`, not `.npmrc`), instead of suggesting a registry check that cannot be the cause.
