`plugin add` and `plugin reload` fixed from a live install (issue #90). **A refresh no longer evicts what `add` installed**: a fetched plugin's dependencies live in its own `.plugins/` cache directory, which is the subtree a refresh dropped whole — so `reload` was structurally impossible for every http plugin with a dependency. Only the fetched half is dropped now, and a refreshed manifest declaring a new dependency gets the same install offer `add` makes. **A failed reload is a no-op, not an outage**: the evicted source is set aside rather than deleted, so a reload whose load fails restores the copy that was working and loads that, reporting which happened. And an install that fails on a workspace-provided peer is explained rather than mis-advised — `describeInstallFailure` recognises an unresolvable *dependency* of the package asked for in a pnpm workspace and names the setting (pnpm >= 10 reads `linkWorkspacePackages` from `pnpm-workspace.yaml`, not `.npmrc`), instead of suggesting a registry check that cannot be the cause. **A failed `add` no longer leaves the package behind**: the npm route installed with a package manager and kept the install even where it then disowned the plugin, worst at the duplicate-name guard, which returns before config is written — so `plugin remove`, the one path that offers to uninstall, had no entry to address it by. The three disowning paths now take it back out, only ever a dependency the same call introduced, and a bare npm name's clash is caught before the install rather than after it.
