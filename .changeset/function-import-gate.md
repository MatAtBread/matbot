A `tool_function` body's module access is gated: the first time a body imports something, the user is asked, naming the function and the module. The decision is keyed on the PAIR `"<function> <specifier>"`, not the specifier alone — "why is this function asking for `node:fs`" is the question being put, and a specifier-only key would let a brand-new function inherit every grant a reviewed one had earned. This replaces the unconditional `await import('node:…')` of the previous release, which was advertised in the generated dts and gated by nothing.

`function_imports: { permit: [...] }` in `matbot.yaml` is an optional RESTRICTION on what may even be asked for. Absent means no restriction, because a gate that is never reached is not a gate — an allow-list defaulting to empty refuses before anyone can be asked, which is the behaviour a prompt exists to replace. `permit: []` is the opposite of absent and switches imports off; it is the only way to say "never", since a standing answer is always a yes and there is no remembered no.

`PermissionRequest` gains `standing` — the answers one act may be remembered as, narrowest first, each as the subject a policy would store and the prose a human reads. The call site supplies the subjects because only it knows how its own generalise, so `default-gate` matches by set membership over strings it never parses: no gate id is hardcoded in the policy, and a gate this build never compiled against generalises on the same terms. It supplies the labels for the same reason it supplies `label`: a subject is a key chosen to be stable and unambiguous, and keys make terrible prose — `#execute node:fs/` is a correct key and an unusable question, and a policy rendering `Always allow "<subject>"` can only ever show the key. A policy stores only a subject that was actually offered, and with none offered it falls back to naming the subject, which is right for a gate whose subject is already prose (`@x/foo` for `plugin.add`).

`FunctionRunner` gains `permittedImports` (the optional restriction, read by both the capability that imports and the type index that declares the reachable set; absent ⇒ unrestricted, `[]` ⇒ none) and an optional `import()` (how a specifier becomes a module — node materialises an `http(s)` URL under `.plugins/` and imports from disk, since it refuses the scheme outright; a browser imports a URL directly).

`import(…)` keeps working as written: `function-tools` rewrites it onto an injected gated loader. `import` is a reserved word, so there is nothing to shadow — and the rewrite keeps a **computed** specifier working, since the argument passes through and the gate sees the string the body actually built. It is a scanner rather than a regular expression because a body that generates source containing `import(` is ordinary, and template nesting and regex-vs-division defeat a single pattern.

The vm runner no longer installs an `importModuleDynamically` callback, which makes a raw `import()` inert through every route, and it withholds `process`, `globalThis`, `global`, `Buffer`, `eval`, `Function` and the phantom `require`/`module`/`exports`/`__dirname`/`__filename`. `process.getBuiltinModule` otherwise reaches every builtin with no import at all, so without this the gate would be decorative. This is not a sandbox and is not described as one: `(()=>{}).constructor('return process')()` recovers the real `process`, and a non-builtin module is loaded as host code that is not shadowed at all — which its gate label says.

`ToolTypeIndex.check` scopes node's types with `paths`, one entry per reachable module, replacing `types: ['node']` — every builtin when nothing is restricted, that subset when something is. That is correctness, not tidiness: `types` makes every builtin resolve unconditionally, so a module the install forbids typechecks clean and is refused only at run time. It also pulls 65 files where `types` pulled 168. A fixed `__dirname` hint no longer recommends `process.cwd()`, which the runner now withholds.

Known weakness, accepted: the grant keys on a function's name, so redefining it under the same name inherits the grant. Keying the body would re-ask on each of the two or three attempts a model commonly needs, pushing a human towards the broadest standing answer on offer.

The prompt offers a module's directory AND its protocol where they differ, rather than one chosen by the specifier's shape. Picking by shape made the available answer depend on which module a function happened to import first: `node:fs/promises` offered "any fs submodule" and never "any builtin", and `node:os` the reverse.

A `permit` entry matches exactly or as a prefix ending at a boundary — its own trailing `/` or `:`, or the next `/` in the specifier. A bare `startsWith` let `https://esm.sh/lodash` admit `https://esm.sh/lodashhack/x.js`. One gate decision is cached per specifier per invocation, so a body importing inside a loop neither re-prompts a human nor re-reads the policy's settings on every pass. And an `execute` body's subject is `#execute`, not `execute`, because a defined function may legitimately be called that and would otherwise share one-off bodies' standing answers in both directions.

Two `tool_function` papercuts measured from a real session, where a model spent five rounds fighting the syntax. `define`'s contract now unwraps a declared `Promise<…>`, as `package`'s already did: `checkSnippet` ADDS a `Promise<…>` to verify the body against, so `f(): T` and `async f(): Promise<T>` describe one tool — but the declared type was spliced into the contract verbatim, so the second made `tool.f()` resolve to `Promise<T>`. `await` hid that (it unwraps recursively) and `.then(r => r.x)` did not, while tsc's own "Did you forget to use 'await'?" pointed at the one thing already correct. And the `name` parameter's description told a model to pass `name` on a `define`, which the contract has no arm for; a defined tool is named by the method name in its own source, and `name` now says so. The cast gate also gained a hint for `Object.keys(x as object)`, where the cast was never needed.
