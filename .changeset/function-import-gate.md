A `tool_function` body's module access is gated: the first time a body imports something, the user is asked, naming the function and the module. The decision is keyed on the PAIR `"<function> <specifier>"`, not the specifier alone — "why is this function asking for `node:fs`" is the question being put, and a specifier-only key would let a brand-new function inherit every grant a reviewed one had earned. This replaces the unconditional `await import('node:…')` of the previous release, which was advertised in the generated dts and gated by nothing.

All of this is the node `FunctionRunner`, which is a PLUGIN — `@matatbread/matbot-function-runner-node` — and is **not installed by default**. Without it a body is compiled with `new AsyncFunction` and runs unbounded, with nothing withheld from it and its `import()` reaching whatever the platform resolves, unasked; the declarations it is written against say so. Add the package to `plugins:` for any of the behaviour described here. Every feature of it is reachable through the `FunctionRunner` seam alone, so an installation wanting a worker, a subprocess or another language replaces one package and touches no core.

`timeout_ms: 0` removes the TIME bound and nothing else. It used to seed no `FunctionRunner` at all — a documented way to run bodies unbounded — which silently discarded the import restriction, unshadowed every withheld global, and made a raw `import()` work, because one setting about how long a body may compute was answering what a body may reach.

`permit_imports` — the runner plugin's setting, authored under `default_settings:` — is an optional RESTRICTION on what may even be asked for. Absent means no restriction, because a gate that is never reached is not a gate — an allow-list defaulting to empty refuses before anyone can be asked, which is the behaviour a prompt exists to replace. `[]` is the opposite of absent and switches imports off; it is the only way to say "never", since a standing answer is always a yes and there is no remembered no.

`PermissionRequest` gains `standing` — the answers one act may be remembered as, narrowest first, each as the subject a policy would store and the prose a human reads. The call site supplies the subjects because only it knows how its own generalise, so `default-gate` matches by set membership over strings it never parses: no gate id is hardcoded in the policy, and a gate this build never compiled against generalises on the same terms. It supplies the labels for the same reason it supplies `label`: a subject is a key chosen to be stable and unambiguous, and keys make terrible prose — `#execute node:fs/` is a correct key and an unusable question, and a policy rendering `Always allow "<subject>"` can only ever show the key. A policy stores only a subject that was actually offered, and with none offered it falls back to naming the subject, which is right for a gate whose subject is already prose (`@x/foo` for `plugin.add`).

`Tool` gains `gateNamespace` — the fixed gate namespace a tool whose NAME is built at run time declares, since `ctx.gate`'s suffix is qualified with the tool's registered name. A `function-tools` function says `tool_function`, so every body's import decision lands on `tool_function.import`. Qualified by the function's own name, each definition would mint its own gate id: nothing stable for `default_settings:` to key, no remembered answer able to generalise across functions (the offered "any function" answer could never apply), one settings key per name the model ever picks, and the only part of this a MODEL controls sitting between it and the gate. It is as trusted as the name beside it — the registering plugin chooses both, and a loaded plugin has full host capability regardless. `bindGate` now takes the resolved tool rather than its name, so the rule lives in one place instead of at each door; a bare name is still accepted for a caller that has only one.

`importPermitted` is exported from `plugin-api` beside `FunctionRunner.permittedImports`: the boundary rule the interface documents, as a function, because two packages read the same list and must agree. `function-tools` decides whether to ask about an import and `tool-types` decides which modules to TYPE, and a copy each diverged exactly where it hurts — `node:fs` admitted `node:fs/promises` at the gate while the checker declared only `node:fs`, so a permitted subpath failed the check and could be imported only with `noTypeCheck`.

`FunctionRunner` gains `permittedImports` (the optional restriction, read by both the capability that imports and the type index that declares the reachable set; absent ⇒ unrestricted, `[]` ⇒ none) and an optional `import(spec, options?)` (how a granted specifier becomes a module, with the import's own second argument passed through so an import attribute works).

A body imports by name only: a node builtin or a package already installed where matbot runs, never a path or a URL. `importableByName` (exported from `plugin-api`) is the rule, applied by the gate before anything is asked, by the runner, and by IMPORT-GATE at the check. Downloading or placing code is a plugin install's job. Paths also defeated the restriction, which matches strings — `./lib/../../x` "starts with" `./lib/` — so a `.`/`..` segment in a package subpath is refused too, and `importPermitted` admits nothing the rule refuses.

`import(…)` keeps working as written: `function-tools` rewrites it onto an injected gated loader. `import` is a reserved word, so there is nothing to shadow — and the rewrite keeps a **computed** specifier working, since the argument passes through and the gate sees the string the body actually built. The rewrite PARSES: node's `stripTypeScriptTypes` erases the types in place (so every line number in what runs is the one the author wrote), then TypeScript's own parser finds the call expressions whose callee is the `import` keyword and each keyword's span is spliced.

This was a hand-written scanner, and it could not be made correct. Telling an `import(` in code from one inside a string, a template, a comment or a regex literal needs the previous significant token, and getting it wrong does not misread one token — it DESYNCS, so a quote further along swallows an `import(` that neither reading mentions, leaving an import with no gate in front of it and nothing reporting that. Two cases are undecidable without having parsed: a `/` after `)` may follow `if (…)` or `(a + b)`, and after `}` it may end a block or an object literal. A parser also tells a method shorthand named `import`, and a type-position `import('x').Foo`, from a call.

`ENV-GATE` leaves the SOURCE half of a renamed destructuring alone — `const { Buffer: B } = await import('node:buffer')` is a property of the module being unpacked, not the global, and firing on it recommended almost exactly the code it was rejecting. It rejects every global the runner withholds, not only the ones a module wrapper would have supplied: `process`, `Buffer`, `globalThis`, `global`, `eval` and `Function` join `require`/`module`/`exports`/`__dirname`/`__filename`. That half is the worse half to omit — `eval` and `Function` are `lib.es` globals, so they typecheck in every configuration and fail at the first call, while `process.cwd()` drew only tsc's "install type definitions for node", which is advice to make a withheld global typecheck. A withheld global named in a TYPE is exempt, since types are erased before a body is compiled.

`unwrapPromise` matches angle brackets instead of pattern-matching them, and unwraps each arm of a top-level union. The greedy form read `Promise<A> | Promise<B>` as one `Promise<…>` and produced `A> | Promise<B` — not a type at all, spliced verbatim into both the generated dts's `ToolContracts` arm and the wire text a model reads, where nothing downstream could recognise it as broken.

The terminal numbers a `select` once its options no longer fit the prompt line, and resolves an exact value or label, then a position (only where numbers were actually shown — the inline form displays none, and `ask_user` may legitimately offer `['2', '4', '8']`), then a UNIQUE prefix of either. An answer matching nothing is returned verbatim where the field allows free text (`allowOther`), as the web frontend does with it. It used to resolve a label prefix only, with a silent fall back to the field's default — which was adequate while every select was two or three short words and stopped being adequate when this gate began offering standing answers as prose: four labels sharing ~50 characters, so the middle ones could not be typed at all and a near-miss read as a denial. An unmatched answer now says so and re-asks once; an empty line is still the default.

The vm runner no longer installs an `importModuleDynamically` callback, which makes a raw `import()` inert through every route, and it withholds `process`, `globalThis`, `global`, `Buffer`, `eval`, `Function` and the phantom `require`/`module`/`exports`/`__dirname`/`__filename`. `process.getBuiltinModule` otherwise reaches every builtin with no import at all, so without this the gate would be decorative. This is not a sandbox and is not described as one: `(()=>{}).constructor('return process')()` recovers the real `process`, and a non-builtin module is loaded as host code that is not shadowed at all — which its gate label says.

`ToolTypeIndex.check` scopes node's types with `paths`, one entry per reachable module, replacing `types: ['node']` — every builtin when nothing is restricted, that subset when something is, expanded by the same boundary rule the gate uses. It pulls 65 files where `types` pulled 168. A fixed `__dirname` hint no longer recommends `process.cwd()`, which the runner now withholds.

A builtin whose name already carries the prefix is typed too: `module.builtinModules` lists `node:sea`, `node:sqlite`, `node:test` and `node:test/reporters` with it, having no unprefixed spelling, so prefixing unconditionally wrote `node:node:sqlite` and those four got no `paths` entry at all — `await import('node:sqlite')` then failed the check with the exact "install type definitions for node" message IMPORT-GATE exists to replace.

`paths` cannot ENFORCE the restriction, though, so a structural rule does: **IMPORT-GATE**, beside the cast gate and ENV-GATE in the one checker. Loading a single builtin's declaration file drags in the ambient `declare module 'node:…'` blocks of everything its own declarations reference (`node:fs` reaches most of the rest through `node:stream`), and whether tsc then resolves a forbidden specifier depends on what `@types/node` is reachable from the program root — so the `paths` set decides what is typed and the rule decides what is allowed. It also replaces what tsc says when the module genuinely does not resolve: "Do you need to install type definitions for node?", about a module the *installation* forbids, which the author cannot act on. Only a literal specifier is checked; a computed one is the gate's at the call, which is where it was always going to be decided. And `check`'s program root is now absolute: a relative one made `ts.createProgram` normalise the virtual file's name to something the host never matched, so there were no files to check and every snippet came back clean whatever was in it — the one failure mode a check gate must not have.

Known weakness, accepted: the grant keys on a function's name, so redefining it under the same name inherits the grant. Keying the body would re-ask on each of the two or three attempts a model commonly needs, pushing a human towards the broadest standing answer on offer.

The prompt offers a module's directory AND `node:` (any builtin) where they differ, rather than one chosen by the specifier's shape. Picking by shape made the available answer depend on which module a function happened to import first: `node:fs/promises` offered "any fs submodule" and never "any builtin", and `node:os` the reverse.

A `permit` entry matches exactly or as a prefix ending at a boundary — its own trailing `/` or `:`, or the next `/` in the specifier. A bare `startsWith` let `lodash` admit `lodashhack/x.js`. One gate decision is cached per specifier per invocation, so a body importing inside a loop neither re-prompts a human nor re-reads the policy's settings on every pass. And an `execute` body's subject is `#execute`, not `execute`, because a defined function may legitimately be called that and would otherwise share one-off bodies' standing answers in both directions.

Two `tool_function` papercuts measured from a real session, where a model spent five rounds fighting the syntax. `define`'s contract now unwraps a declared `Promise<…>`, as `package`'s already did: `checkSnippet` ADDS a `Promise<…>` to verify the body against, so `f(): T` and `async f(): Promise<T>` describe one tool — but the declared type was spliced into the contract verbatim, so the second made `tool.f()` resolve to `Promise<T>`. `await` hid that (it unwraps recursively) and `.then(r => r.x)` did not, while tsc's own "Did you forget to use 'await'?" pointed at the one thing already correct. And the `name` parameter's description told a model to pass `name` on a `define`, which the contract has no arm for; a defined tool is named by the method name in its own source, and `name` now says so. The cast gate also gained a hint for `Object.keys(x as object)`, where the cast was never needed.

A type-check verdict names the environment it was reached in. `ToolTypeIndex` gains an optional `environment()` — a fingerprint of what a check depends on besides the snippet and the live tool types: whether a `FunctionRunner` is loaded, what it permits a body to import, and which globals it does not bind — and `ToolCheckReport` carries it on any verdict that exists. `function-tools` stores it beside each definition (a global function, a package, a session function's marker) and compares it for equality, reporting `checkedElsewhere: true` in `list` and `check` where it differs. Without this a verdict was a claim about a possibly-different environment: unload the runner plugin or narrow `permit_imports`, and a body that passed stays marked as having passed while its `import(…)` is no longer gated, or no longer allowed at all. Nothing re-checks on load — that is a worker program per stored function at boot, and would turn a report into a boot failure — so what changes is that the report tells you, and `check` remains the way to re-verify.

tsc's "Do you need to install type definitions for node?" no longer reaches a function body. It arrived for a withheld global (TS2591 on `process`) whenever NO runner was loaded, because then nothing is withheld and ENV-GATE has no list to fire from: advice to run a package manager, aimed at an author with no package.json and no say in what the runner declares. The finding stands and the message is replaced, keyed on tsc's own diagnostic code rather than on a second list of names, so it cannot drift out of step with what the runner withholds.

The browser `ToolTypeIndex` answers `environment()` for the contract's sake and nothing compares it: `check` reaches no verdict there, so nothing stores a fingerprint. Its `dts()` does now carry the import note it previously omitted entirely — a body in the browser was told nothing about imports at all.

`function_runner_config` (`get`/`set`/`clear`) reads and changes the runner plugin's two settings at run time. They are a plugin's settings, so exposing them is the plugin's job and the write path is the ordinary per-principal override above the `default_settings:` floor — `set` rebuilds the runner through the same function `setup` uses, so narrowing what a body may import no longer waits for a restart, and nothing downstream needs invalidating (every consumer reads `services.FunctionRunner` at the point of use, and the type index's `paths` cache keys on the permitted array by identity). `null` for a key reverts it to the installation default, which is what `delete` means on a layered setting and is NOT the same as no restriction. Each key is gated separately: what a body may reach and how long it may compute are two decisions, and a standing answer for one must not carry the other.

Two consequences are stated rather than left to be found. Reads are layered, so a stored override beats the configured floor and can WIDEN it — the honest claim about `permit_imports` is that it is what no answer at the import prompt can lift, not that it is out of a running actor's reach, and an installation needing the latter ships a runner with the list compiled in (a package swap, no core change). And a settings override is per principal while the runner is one object per process, so a change is the environment every principal in that process then gets.

The runner's settings are validated wherever they come from — `default_settings:` and a hand-edited document as well as `function_runner_config set`. A bad `timeout_ms` falls back to the default and a bad `permit_imports` to `[]` (imports off, never "no restriction"), each warned at boot and reported by `get` as `problems`. An import label no longer implies a builtin is a narrow grant: `node:child_process`, `node:module` and `node:process` each reach full host capability, so a builtin's label says so, as a package's always did.
