# The LLM is an ALU: Why Your AI Agent Needs a guy who wrote games on a ZX Spectrum

*Matt*

---

A few weeks ago I was mid-sentence, explaining to my own agent why one of its habits was wasteful, when the habit fired. We were discussing — in the conversation itself — how a skill called "Remember This" was burning four LLM round-trips to do the work of one database write. While I was typing that sentence, the trigger matched, and the thing did it again: a robo message, three tool calls, a summary, and finally — four turns later — the fact landed in storage. The runtime had every piece of data it needed before the model even knew there was a conversation to react to. It was like hiring a concert pianist to press the "on" button on a CD player, and watching him do it with feeling.

I laughed, and then I stopped laughing, because I recognized the shape of the problem. I'd seen it before, just never wearing this costume.

## What kind of machine is this, actually

The instinctive way to think about a large language model is as a slow, occasionally unreliable processor. Give it better prompts the way you'd give a CPU better-optimized code, give it more context the way you'd give it more RAM, wait for the next model generation the way you'd wait for a clock-speed bump, and the rough edges — the forgetfulness, the drifting attention, the tendency to lose the plot four tool calls into a procedure — will sand themselves down. This is, I think, the consensus view, and it's wrong in a way that matters, because it assumes the LLM is a machine with the *kind* of deficiency that more resources fix. It isn't. It has a deficiency that's definitional, not incidental.

A CPU has a program counter. It has registers. It has a fetch-decode-execute cycle that advances on its own, instruction after instruction, whether or not anyone's watching. None of that requires intelligence — a $2 microcontroller has all of it. What it requires is *state that persists between operations*, and a mechanism for deciding what to do next based on that state. An LLM has neither. Hand it a token matrix, get a token matrix back, and the moment the call returns, every trace of "where it was" is gone. The only state it has is the state you handed it on the way in. Call it again with the same input and you get — near enough — the same output. There's no thread running underneath that remembers it was halfway through a plan.

This is why I don't think "not Turing complete" is overstating the case, even though it sounds like a much bigger claim than it is. A Turing machine, at minimum, needs unbounded read-write memory it can consult and revise as it runs. An LLM, by itself, has no memory it revises — it has an input it transforms once, in one pass, with no internal loop. It's not that it's a *weak* general-purpose computer; it's that it isn't a sequencer at all. It's the part of a computer that does the actual computing — the arithmetic-logic unit — wearing the entire system's clothes because nobody's built the rest of the system around it yet. Worth being blunt about this, because it's the crux of everything that follows: LLMs aren't computers, so they struggle to run your programs. A program is a sequence of steps where each one depends on what happened at the step before. There is no "before" inside a single forward pass — there's just this pass, this input, this output. LLMs don't "compute", they _simulate computation_ in a single state.

And that's the part that makes "wait for the next model" a category error. A faster, smarter ALU is still an ALU. You can make the matrix multiply bigger, the context window longer, the next-token prediction sharper, and you will absolutely get a better-behaved ALU — fewer arithmetic errors, a wider operand. What you will not get, no matter how far you push it, is a program counter, because a program counter isn't a capability you scale into existence with more parameters. It's a different *kind* of thing, bolted on from outside. Attention deficit, context bloat, the habit of forgetting an instruction given ten turns ago — these aren't bugs in the LLM (or ALU). They're the entirely predictable consequence of asking a stateless function to behave like a state machine by reloading the *entire* machine's state through its only input slot, every single time, and hoping nothing gets dropped on the way in. Bigger context windows make that slot bigger. They don't give the ALU anywhere to put things it isn't actively being handed right now.

## Build the rest of the processor

I grew up on machines where you couldn't pretend this problem away, because the hardware made the boundary between "the part that computes" and "the part that remembers and sequences" completely explicit, in silicon, on a data sheet you could read over breakfast. So when I recognized the shape of the LLM problem, the instinct that kicked in wasn't "prompt it better." It was the much older one: if the compute core has no state and no sequencing of its own, you build it around the core, the way every processor architect since the 1970s has, and you get to steal sixty years of hard-won lessons about exactly how to do that.

In an earlier life, I worked on an early phone called the Pogo I built the kernel for in 2001 running on a 33MHz ARM7. A full context switch there was six instructions: push every working register to a context block, swap a global pointer, pop the new task's registers back in. Microseconds. It worked because the ARM7 had single instructions for multiple register read/write, meaning the hardware had already half-finished the job — and we leaned on that further, deliberately leaving one register unrestored on the way out of an interrupt so the C routine doing the actual switch could smuggle a return value through it. None of this was clever in the way people mean when they say "clever code." It was clever in the older sense: knowing exactly what state exists, exactly where it lives, and exactly when it's safe to touch — and then doing the absolute minimum required to move it.

Once you've internalized that the *first* job is always "give the stateless core somewhere to keep state, and a counter that says what's next," the rest of processor history reads less like a museum and more like a checklist of problems you're about to have. Stacks and call frames are what happen the moment your code wants to call a subroutine and come back — you need somewhere to remember the return address, and a discipline for nesting those reliably. Interrupts are what happen the moment something *outside* the sequence — a keypress, a timer, an incoming packet — needs to change what runs next without the running program asking for it; you save state, vector to a handler, restore, resume, and the trick is making that save/restore cheap enough that you can afford to do it constantly. Memory banking is what happens when your address space is smaller than your problem, so you swap fixed-size windows in and out of a fixed-size frame and accept that, for a while, half your program simply isn't visible to the other half. MMUs are what happen once you get tired of managing that swapping by hand and push it down into hardware that does it transparently — the program just touches an address, and if the right page isn't resident, a fault handler fetches it and the program never finds out anything happened at all.

And once the processor's sorted, the operating system on top of it has its own parallel set of lessons, learned the hard way over the following two decades: heap management, because not everything fits neatly into a stack discipline and some allocations genuinely outlive the call that created them; hardware abstraction, because you want the software above a device to work whether that device is a 5MB/s hard disk or a RAM cache, as long as both speak the same protocol; proper context switching at the process level, not just the register level, because two programs sharing one CPU need the illusion of having it to themselves; and, eventually, compilers, because once you've written the same procedural pattern by hand for the tenth time, you stop hand-translating intent into instructions and build something that does it for you, once, so every future run pays only the cost of running, not the cost of re-deriving.

None of this required the processor to get smarter. The 8080 didn't become the 8086 by getting better at arithmetic — multiplication on an 8080 is still multiplication on an 8086, mostly. It got more useful because more got built around it: more state, more ways to sequence and interrupt that state, and eventually a whole abstraction layer that let you stop thinking about the silicon at all. The lesson transfers exactly, because the gap it's closing is exactly the same shape.

## So what does this mean for a harness

This is the question I started actually answering instead of just complaining about, and the answer is matbot — an agent framework where every one of those old lessons shows up doing real work, not as decoration.

The state the LLM doesn't have lives in **stores**: typed, addressable, durable collections that plugins read and write directly, without a round-trip through the model, but the model can access via a strict protocol. Session history is the accumulator — the one piece of state that's always handed back in on the next call. That is most of why context management is the central cost problem in this whole field, and it's not a problem more parameters fix; it's a problem of how the session is managed, in the same way a heap is managed by an OS.

The program counter is just code — ordinary, boring, debuggable TypeScript doing the fetch-decode-execute work the model can't: deciding what happens next, looping, branching, calling the model exactly when a genuine judgment is needed and not one call before or after that. **Hooks** are the interrupt lines: an event fires — a message arrives, a turn completes, a tool returns — and registered handlers run, synchronously, deterministically, with the model involved only if a handler decides it needs to be. **Triggers** add the vectoring: a condition (a cheap, single-turn, context-free classifier call) decides whether the interrupt fires at all, the way a peripheral's interrupt-enable bit decides whether its request even reaches the controller.

Before any of that existed, the way we forced the model's hand was by writing a fake message into the conversation and hoping it noticed — a "robo message" that looked like the user had just said something, when really the harness had said it on their behalf. It worked, in the way certain 1980s tricks worked: it was a `JMP` into a self-modifying trampoline, because you wanted an indexed indirect jump but you were running from ROM, and anyway the CPU designer forgot that instruction. Set up a return address by hand, jump to that routine in RAN and hope nothing on the way back clobbers the stack. The actual problem is that the model's own API gave you no way to inject anything into its output stream, just like the CPU designer didn't bother with the complex jump. You couldn't patch the interrupt vector table, because the vector table was, functionally, baked into mask ROM, or the LLMs training in this case. The moment the API let code inject a tool call directly, the robo message stopped being a workaround and became a museum piece: skill trigger system, circa 2025, note the hand-crafted trampoline, elegant in its way.

Two of the lessons from operating-system development show up around the **mount table** — the registry where plugins announce the services they provide (a storage backend, a knowledge index, a skill manager) and the rest of the system discovers them, the way a bus lets you plug in a card without redesigning the motherboard around its specific pinout. The harder lesson is what happens when you unplug the card. Unload a plugin and the obvious failure is a dangling reference — something still pointing at a storage backend that no longer exists, working only by luck until the moment it doesn't. The less obvious failure, and the one that took longer to see, is the opposite: a *strong* reference that keeps the unloaded plugin's entire working set alive in memory, the agent-framework equivalent of a driver that never released the device it was holding open. The fix has the same shape as any resource-acquisition discipline: whatever reacts to a service appearing has to react, symmetrically, to it disappearing — tear down the hook it registered, drop the cache it built, release the reference it was holding — rather than leaving a hook resident and silently failing on every single turn for a dependency it already knows is gone.

The clock matters here too. The moment you have multiple things — a turn completing, a plugin unloading, a storage backend being swapped out from under a live session — that can mutate shared state, you have the same race condition a synchronous digital circuit was invented to avoid: nothing commits mid-cycle, only at an edge. matbot's version is a *quiescent edge* — no turn, no hook, no tool call currently in flight — and every pending change (a new backend taking over, a plugin's services appearing or disappearing) queues up and lands there, all at once, instead of wherever in the turn it happened to be requested. Once that was in place, the whole machine, or in this case the LLM harness, could fairly be called "clocked," and clocked systems are the ones you can actually reason about.

Memory banking and the MMU both show up around **skills**. Loading a skill into context the old way — catalog them all in the system prompt, how the model picks the right one at the right time, paste it in, let it sit there for the rest of the conversation — is exactly bank-switching done by hand and never undone: you've paged something in, and there's no `free()`, so it just occupies the window until the conversation ends. `contextual_search` is the closer analogue to a real MMU: the model talks normally, with _no skills catalog and no skills in context_, and only when it hits a concept it doesn't recognize — a page fault, properly speaking — does it call the `contextual_search` tool, which fires a reranker and pages the relevant skill in. You pay for the misses, not the hits, and that ratio is the entire reason demand paging beat "load everything up front" decades before anyone here was calling it that. The piece we don't have yet, and I don't think anyone does, is the eviction half — a real replacement policy for context, the way an MMU pages things *out* under pressure, not just in on demand. Right now the only eviction we have is the ephemeral trigger — content scoped to live for exactly one turn and then vanish by construction — which is the in-and-straight-back-out overlay, not the general case. That's an honest gap, but matbot has an architecture that means a more algorithmic eviction is possible, rather than just hoping the LLM just ignores the now irrelevant skill.

The compiler-versus-script lesson shows up almost unchanged. Two skills — "Remember This" and "Dream Time" — started life as markdown the model interpreted procedurally by the LLM, with all the risks that the LLM would elide tests or commands, paying full token cost for every heading and branch whether or not that branch was taken on a given run. We wrote a "skill compiling skill" that plays to the LLMs strengths: great at writing code, not so good at following detailed instructions. Both "Remember This" and "Dream Time" were compiled to TypeScript and made available as _tools_ that handle the actual sequencing and call the model exactly once each, for the one decision that's genuinely a judgment call (does this fact belong with that skill, and how should it merge in?) — while ordinary code does the iteration, the retries, the bookkeeping. Because *matbot* has hot-loading of plugins, the compiled tools can be loaded *on-demand*, with no re-deploy or restart. The LLM can take procedural skills written as markdown and generate a TypeScript replacement that can be loaded, tested and debugged. The cost of the interpretation, which was previously paid on every use of the skill, is now a single compilation cost amortized over every use of the tool — and the calls the tool makes afterward are straight TypeScript invocations. The result is skills that are faster, more observable, more reliable, and much, much cheaper in terms of both context and cash.

The background pipeline that grew out of that, `dream_time`, runs unattended: it ranks unassigned facts against every skill's metadata and merges the matches, calling the model for exactly two narrow steps, with everything mechanical happening in code that never touches the model at all. There's a real compiler for this now, shipped as `skill_compiler`: feed it a markdown skill, get back a TypeScript plugin that does the same job without re-interpreting the instructions on every single use. You don't read its output any more than you read what `tsc` emits — it's object code, and the markdown stays the source of truth you'd actually go back and edit. Not everything should go through it; a skill that's a narrative or a reference table has no procedure to compile. But a skill that's a workflow with branches and bookkeeping was never really a skill. It was a program someone hadn't gotten around to compiling.

## What this isn't

I'll admit the risk in all of this, because it's a real one and I'd rather name it than pretend it isn't there: once you've spent decades thinking in interrupts and page tables, you start seeing every problem with LLMs as a systems-engineering nail, and reaching for the hammer regardless of whether the screw in front of you actually wanted one. Not every skill needs compiling. Not every context problem needs a session manager modelled on a heap manager. You don't put virtual memory in a thermostat, and you don't wrap a tool around a task whose entire value is the model doing the work, badly drawn analogy or not.

But naming the risk doesn't make the underlying parallel less real, and it's worth being precise about what's actually parallel and what isn't. Early computers had expensive cycles and scarce memory, so they grew IO, schedulers, interrupts, and paging. LLMs have expensive tokens and scarce context, and the exact same shape of problem is showing up: what to keep resident, what to fetch on demand, what to hand off to something cheaper, what to never let the expensive unit touch at all. None of this is a claim that the model is bad, or that this approach is somehow cleverer than just waiting for better models. It's closer to the opposite: the model is, for what it actually is — a combinatorial transform over an enormous operand — extraordinary, and getting more extraordinary every year. What it will not become, by getting bigger, is a sequencer, because a sequencer was never a property of the function; it's a property of the system you build around the function. Moore's Law never fixed anyone's memory management either — it just made it cheaper to get away with not doing any, for a while, until the workloads grew to fill whatever you'd been handed. The fix, then and now, was never going to come from inside the chip.

What surprised me, going through this, wasn't that the analogy worked. It was how *completely* it worked — how a kid who spent the 80s counting bytes on an 8-bit machine with 8K of RAM, and the 90s and 2000s building kernels and context switches for processors most people have never heard of, turned out to have already learned, decades early, exactly what it takes to get something useful out of a component that's powerful, expensive, and fundamentally incapable of remembering what it just did.

None of which is really about matbot. matbot is just the one example I happen to have wired up and watched fail in exactly these ways — proof the lessons transfer, not the point of writing them down. The actual claim is narrower than "use my framework," and I think more useful: an LLM is a logic gate, not a computer, and the part of your system that turns out to be unreliable is rarely the gate itself. It's the sequencing, abstraction, storage management, the interrupt handlers. Things a longer prompt won't ever supply. That's not a prompt problem. It's an architecture problem, and it has the same shape it's always had: decide what's stateful, decide what's resident and what gets paged in on demand, decide what runs to completion and what gets interrupted, and build that around the part that just transforms input into output. Whatever you're building, that's worth sitting with before reaching for the next model release. Build the rest of the machine, and the ALU you already have will turn out to be enough.
